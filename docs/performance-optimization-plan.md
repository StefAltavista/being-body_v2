# Website performance optimization plan

Prepared 7 September 2026 against repository commit `cb3fce1`. Scope: homepage scroll smoothness first, then image delivery and rendering across the website. The highest-priority, appearance-preserving package described below has now been applied; the remaining rendering experiments stay intentionally deferred until a representative production trace is available.

**Applied package (8 September 2026).** The public image graph was audited from active app routes and all 144 unreachable image assets were removed. The published image set is now 47 referenced files (about 8.0 MB, down from about 1.05 GB before cleanup), with no missing references. Used PNG artwork was converted to lossless WebP with decoded visible-pixel checks. The homepage concept artwork now has browser-rendered, pre-blurred/pre-tinted 1× and 2× WebP derivatives for the desktop path; the mobile path retains the existing CSS filters so its fixed-pixel blur remains unchanged. The homepage portrait and the three large therapy/booking photographs were resized to the largest display width that their containers can reach and encoded as quality-88 WebP; together with the oil photographs and logos resized to 1200/800 px ceilings, these derivatives remove about 31.7 MB from the used image set. The booking bubble now uses the same coordinates through transform x/y properties, removing layout-property animation from the moving bubble while preserving the original path, timing, scale, pinning, and section collapse. Homepage card `sizes` now reflects the transformed artwork's required candidate width. Existing blur, hue, saturation, pinning, and mobile behavior were deliberately kept intact.

**Recommendation:** retain GSAP and the visual identity. First reduce the cost of the animated surfaces and eliminate layout changes during scrolling. Then improve responsive image selection, asset preparation, loading, and caching. Compression alone is unlikely to resolve sustained scroll lag.

**Evidence and limitations.** The audit inspected the homepage component tree, shared layout, animation code, other routes, the installed Next.js image implementation, local asset metadata, and emitted homepage HTML. It also encoded representative images in memory with Sharp. The installed versions are Next.js 15.5.15 and Sharp 0.34.3. The repository uses GSAP 3.x and React 19.

The public URL `https://beingbody.net/` displayed a different, older site with hash navigation and different content. The matching production/preview URL is still needed for a representative performance trace. A fresh webpack production build now completes successfully; this sandbox does not allow binding a local listening port, so the runtime trace remains outstanding. Existing emitted HTML is useful corroboration of image markup, but is not a runnable, verified baseline. No production FPS, GPU usage, Core Web Vitals, image-response headers, or measured speedup is claimed here. Findings below distinguish code facts from performance hypotheses.

**What is already working.** The site uses `next/image`, including lazy loading and asynchronous decoding in emitted markup. The welcome image has `priority` and `sizes`. Most homepage motion already uses transforms and opacity, and components generally use scoped `useGSAP` cleanup. ScrollTrigger already has `limitCallbacks` and `ignoreMobileResize` enabled. There is no reason to replace these mechanisms before profiling.

**The main homepage findings, in recommended investigation order:**

| Priority | Evidence in this repository | Proposed change | Expected effect and qualification |
| --- | --- | --- | --- |
| P1 | `AnimatedBackground.tsx` scrubs rotation, skew, translation, opacity, and a filter string containing hue rotation, 20 px blur, and saturation. Scale grows from 3.5 to 5 on mobile and 2 to 3 on desktop. Its wrapper allows overflow by default. | Export suitably small, already blurred/tinted artwork; animate its wrapper with transforms and opacity; bound the visible decorative surface and reduce mobile scale/travel. | Strong candidate for reducing raster/compositing cost. Filters can be GPU accelerated, but large filtered surfaces still cost work. Confirm with traces and an effect-off comparison. |
| P1 | `Header.tsx` has a fixed, full-width, 150 px header with a masked `backdrop-blur-3xl` layer above moving content. | Compare a translucent gradient without backdrop blur; if necessary retain only a smaller, localized blur on desktop. | Potential improvement throughout the page, since the backdrop changes while scrolling. |
| P1 | `BookButton.tsx` collapses its section from 400 px to zero by animating height/padding; its moving copy animates `left` and `top`. `HandBubble.tsx` observes the section with ResizeObserver and requests a debounced refresh. | Preserve the section's layout footprint and animate an overlay using x/y/scale. If the footprint must change, design an explicit transition and refresh once after it settles. | Removes a definite source of layout work and moving downstream scroll coordinates. The observer is debounced; the code does not refresh every frame, but the collapse changes layout every frame. |
| P1 | The pinned finale expands `hands_float` by 2.8× horizontally and 2.2× vertically while blurring it to 30 px; several text and ancestor layers also animate blur. | Keep the narrative timing; replace animated blur with fades and modest transforms. Pre-rendered crossfades still add layers, so compare them with a single image. |
| P1 | `Card.tsx` uses `Image fill` without `sizes`; emitted markup defaults to `100vw`. Each background is scaled 1.9× and filtered. | Supply sizes matching the actual responsive card layout; prepare background crops/tints and remove unnecessary overscaling/filtering. | Avoids requesting viewport-wide candidates for cards occupying part of the viewport; reduces image and rendering work where the source has enough resolution. |
| P2 | `Concept.tsx` renders two filtered copies of the same bubble artwork; one reaches scale 3 and skewY −50. | Preserve the composition with smaller pre-tinted variants, less extreme mobile transforms, or one layer in the mobile design. Use stable wrappers as scroll triggers. | Reusing the same URL can share fetching/decoding, but does not eliminate the cost of drawing two transformed layers. |
| P2 | `BookButton.tsx` starts recursive floating animations for both the original and the fixed bubble, including the hidden copy. | Run only the visible bubble's animation; pause offscreen and on document visibility changes; explicitly clean up callback-created tweens. | Reduces ongoing JavaScript work and battery use. |
| P2 | Permanent `will-change` is assigned to backgrounds, practice cards, and several finale elements; global GSAP config forces 3D transforms. | After profiling, use targeted promotion near active scenes and release it when safe. Compare GSAP's automatic 3D behavior with the blanket override. | Layer promotion is a tradeoff; too many or oversized layers can increase memory and compositing cost. |
| P2 | `globals.css` sets a generic 700 ms transition on all h1/h3/p elements; cards use `transition-all` and hover margin changes. | Restrict CSS transitions to intended hover properties; ensure GSAP owns its animated properties without competing CSS transitions; remove hover layout changes. | Prevents CSS transitions from repeatedly retargeting properties GSAP updates and avoids incidental layout work. |
| P2 | The welcome sequence takes 2 seconds for the image, then waits 1 second, then reveals text for 1 second. | Show the critical image/text immediately or use a brief, overlapping entrance with no blur; keep the current LCP image preload. | Improves perceived readiness and may improve LCP. Measure the actual LCP candidate; preload alone does not guarantee prompt visibility. |

Prefer transform/opacity animation and verify paint and layer behavior in DevTools; neither property is a guarantee of zero rendering cost. [Browser animation guidance](https://web.dev/articles/animations-guide). Use `will-change` sparingly and remove it when no longer useful. [MDN guidance](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/will-change).

Next.js already emits optimized image URLs and its installed default output format is WebP, so the source-to-WebP reductions are not additional savings we can promise. The useful comparisons are the current served response versus a corrected width, crop, format, or quality. Test cold-cache encoding latency as well as warm-cache transfers before selecting AVIF.

At 1080×1440, the bubble has about 5.93 MiB of RGBA pixels; at 640×853 it has about 2.08 MiB. AVIF and WebP at the same decoded dimensions have essentially the same pixel count. Actual graphics memory depends on browser tiling, raster scale, intermediate surfaces, and reuse. CSS enlargement does not automatically mean the browser allocates a full enlarged bitmap, but can increase raster/compositing demands. This is why download bytes, decoded dimensions, and visible layer area need separate budgets.

**Image delivery work across the website:**

1. Define image roles: hero photography, card photography, product thumbnails, transparent artwork, blurred decoration, icons, and social previews. Give each a maximum display size, source crop/aspect ratio, target pixel density, and quality policy. Keep high-quality originals outside the published asset set.
2. Fix `sizes` on homepage cards and `fill` heroes in Pilates and massage. Tighten existing sizes on the capped homepage portrait and oil image containers. Derive values from actual computed layout, including padding and breakpoints. Browser candidate selection does not know that CSS transforms will enlarge an image, so balance sharpness at peak scale against the role of intentionally soft decoration.
3. Correct dimension/aspect-ratio declarations. For example, the hands source is 567×509 but is declared 1000×1000; the finale logo source is 100×292 but is placed in a 300×300 contain box. Preserve intentional framing with wrappers and `object-fit`, while using correct source ratios. Next's installed optimizer avoids enlargement for its normal width-only resize, so a large `w` parameter is not proof it serves that many pixels. Existing low-resolution art may need a better master for sharper large display, rather than more compression.
4. Crop portraits to their real use where art direction permits; do not encode large off-crop areas only to discard them with `object-cover`. Generate source derivatives from originals once. Avoid repeatedly converting lossy derivatives or automatically recompressing everything through two lossy stages.
5. Keep true above-the-fold/LCP media prioritized; lazy-load ordinary below-fold photography. Remove blanket `priority` from decorative `Background.tsx` after verifying its visual timing. For an animated image that becomes visible before its layout box enters the viewport, prepare it one section ahead with an observed preload/decode, not a preload of the entire page. Reserve geometry and do not delay all animation initialization on every image's load.
6. Test AVIF with WebP fallback through Next's image negotiation. Preserve alpha and inspect watercolor edges, thin lines, gradients, and color profiles on light/dark backgrounds. Keep SVG icons as vectors; optimize unnecessary SVG metadata if material. Do not replace artwork with SVG filters expecting an automatic performance win.
7. Audit image optimizer/CDN responses: actual content type and dimensions, transferred bytes, cache hit/miss, cache-control, and cold/warm latency. Check whether a proxy forwards `Accept` and handles negotiated variants correctly. The installed image cache minimum is 60 seconds; choose a longer policy only with suitable asset versioning and deployment support. Use immutable long caching for fingerprinted assets, not mutable filenames indiscriminately. Check persistent optimizer cache storage if self-hosted.
8. Remove browser-name-based PNG/WebP selection in About and Contacts when using the Next image pipeline. Let supported format negotiation decide; server-side browser-name detection is not a reliable per-visitor content strategy.
9. Add an asset manifest and validation for missing files, dimensions, unusually large published sources, and intended variants. Check all dynamic paths before excluding archive folders. Fix the social preview separately: metadata declares 1200×630 while the current PNG is 1632×1634; it does not contribute to homepage scroll rendering.

The Image API supports responsive sizing, prioritized loading, configurable formats, and caching. Verify settings against the installed Next 15 release rather than copying Next 16 defaults. [Next.js 15 Image reference](https://nextjs.org/docs/15/app/api-reference/components/image).

**Animation architecture and mobile behavior:**

1. Define full-motion desktop, lighter mobile, and reduced-motion modes using `gsap.matchMedia`. Screen width selects a design, not a guaranteed performance class. Keep conservative mobile defaults; use measured performance or an optional motion setting only if justified. Respond to preference/breakpoint changes and revert old timelines cleanly. [GSAP matchMedia](https://gsap.com/docs/v3/GSAP/gsap.matchMedia()/).
2. Mobile should use one soft background where possible, smaller travel/scales, simpler card reveals, and a short or unpinned finale. Preserve all messages and booking actions. Reduced-motion should present content in normal reading order without scroll pinning, blur reveals, or perpetual motion; also override global smooth scrolling and CSS bubble animations.
3. Use stable wrappers as triggers and animate their children. Keep element measurements out of per-frame updates. Numeric scrub values control catch-up duration, not the update rate; tuning them is a feel adjustment, not a rendering fix. Use a coordinated timeline where it simplifies scene ownership, rather than consolidating every trigger without evidence.
4. Pause independent perpetual animations when not visible or when the page is hidden. Scrubbed scenes must still restore the correct state on re-entry and reverse scroll. Use `once` only for effects intended to run once, not the whole scroll narrative.
5. Consolidate refresh scheduling for actual layout changes. Fonts, loaded assets that affect layout, breakpoint changes, and pin setup can require refresh; avoid redundant custom resize refreshes and test mobile browser toolbar behavior. Preserve ScrollTrigger pinning semantics and refresh order. [ScrollTrigger reference](https://gsap.com/docs/v3/Plugins/ScrollTrigger/).
6. Scope callbacks and explicit cleanup consistently. Existing `useGSAP` usage is a good base; callback-created/repeating animations still need context-safe handling or explicit lifecycle ownership. Test navigation away/back for duplicates and retained resources. [GSAP React lifecycle guidance](https://gsap.com/resources/React/).

**Other routes and shared rendering:**

- `Background.tsx` is a fixed, 4× scaled, filtered image on several pages. Apply the same pre-rendered artwork approach, remove unneeded React viewport-height updates in favor of an appropriate stable viewport CSS unit after Safari testing, and reconsider decorative priority.
- `OilsShowcaseCarousel.tsx`, used on oils listing/detail routes, calls `setPosition` from its animation frame loop and rerenders its card tree while autoplay advances. Keep frame-level transform state in refs/GSAP setters; reserve React state for semantic selection and controls. Stop autoplay work when offscreen/hidden/paused, preserve focus and drag behavior, and avoid CSS transitions fighting continuously updated opacity. Its existing reduced-motion guard is useful but currently checked only at setup. This carousel is not mounted on the current homepage.
- Product carousels should load the visible image and appropriate neighbors, reuse matching source variants for clones, and avoid preloading every product. Inspect real requests before implementing virtualization for the small existing collection.
- `FloatingBubble.tsx` has incomplete offscreen pause behavior, but is not currently imported by the audited routes. Keep it out of the critical optimization path. CSS `Bubble` animations are used on inner pages and should respect motion preferences and visibility.
- Convert the homepage composition to a Server Component and keep animated/interactive pieces as client islands. `Welcome` must gain its own client boundary when the page boundary is removed. Similarly review static inner-page content. This can reduce client JavaScript/hydration, but does not remove GPU costs during sustained scrolling. Server Components can wrap client components and pass static children. [Next.js component boundaries](https://nextjs.org/docs/15/app/getting-started/server-and-client-components).
- Replace the global Google Fonts CSS import with deliberate font loading; prefer licensed WOFF2 assets, controlled preload, and suitable `font-display`. The layout loads Geist variables while global styling uses Amatic/Zeppelin: check whether the Geist preloads are needed. Preserve text metrics so fonts do not shift scroll coordinates.
- Keep Cal.com scripts restricted to booking, and forms/modals loaded when appropriate. Reduce the 200–260 px modal blur effects. Verify bundle composition before changing dependencies; a large server-only package is not automatically client bundle weight.
- Use transform-based menu transitions and intentional hidden-state behavior instead of broad width/padding transitions. Keep keyboard access and focus handling intact.

**Other solution families evaluated:**

| Option | Decision for this site | Tradeoff |
| --- | --- | --- |
| Pre-blurred/pre-tinted raster artwork with transform animation | First choice for decorative scenes | Preserves the style while moving filter work offline; needs visual review and sensible resolution. |
| One small image or simple static CSS gradients | Strong mobile alternative | Reduces overlapping surfaces; exact artwork may differ. Animating gradient stops or adding broad live blur can reintroduce cost. |
| Crossfade two prepared colors/blur states | Prototype if the color transition is essential | Removes the dynamic filter but adds another image/layer and alpha blending. |
| CSS keyframes or Web Animations API for simple loops | Selective use | Can simplify independent transform/opacity loops; does not make large filtered artwork cheap. GSAP remains appropriate for the coordinated finale. |
| Native CSS scroll-driven animation | Progressive enhancement experiment | Potentially useful for simple progress/transforms where supported; feature-detect and test target browsers. Not a drop-in replacement for pinning and multi-stage callbacks. [MDN animation timelines](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/animation-timeline). |
| CSS containment / `content-visibility: auto` | Limited trial on static below-fold sections | Can skip offscreen rendering; requires reserved intrinsic sizes. Avoid blanket use on pinned scenes, fixed descendants, overflow-crossing artwork, or measured trigger ancestors. [Content visibility](https://web.dev/articles/content-visibility). |
| CSS sticky instead of a GSAP pin | Consider for a simplified finale | Can reduce custom pin coordination but changes timeline/layout design. Test overflow ancestors and scroll restoration. |
| Canvas 2D | Defer | Potentially useful for many particles, but these scenes have relatively few elements. Large canvas redraws, scaling, DPR, and accessibility introduce new work. |
| WebGL / OffscreenCanvas / workers | Last resort if profiling justifies a rendering rewrite | Can render specialized effects efficiently, but adds bundle/setup/memory/context-loss handling. Workers cannot move ordinary DOM layout or GSAP DOM animation off the main thread. |
| Scrubbed video / image sequence | Defer unless the art direction changes | Video seeking depends on keyframes and decode; image sequences can have large download/memory costs. Neither is an automatic scroll-smoothness fix. |
| Dedicated image CDN or build-time image generation | Conditional | Useful if measured optimizer latency/cache misses justify it. For this static catalog, build-time derivatives are viable; an external service adds cost and migration work. |
| Service worker / preloading the whole site | Not a first-line fix | Warm caching helps repeat loads but not per-frame drawing; bulk preloading competes with critical content and increases memory use. |
| Smooth-scroll library / normalizeScroll / lower global GSAP FPS | Not a first-line fix | These alter scrolling behavior or cadence rather than eliminate expensive drawing. Lowering FPS can make motion visibly worse. Use normalization only for a demonstrated browser-specific coordination problem. |

**Implementation sequence and effort.** Estimates assume one developer and access to representative devices; they are planning ranges, not promises.

| Stage | Deliverable | Estimate | Exit condition |
| --- | --- | --- | --- |
| 0 — Baseline | Correct deployment URL, fresh production build, traces and image waterfall | 0.5–1 day | Repeatable cold/warm runs; bottleneck ranked by section and device. |
| 1 — Homepage rendering | Background/header comparisons, stable booking geometry, simplified finale, transition cleanup, mobile/reduced-motion modes | 1.5–3 days | Same content/actions; improved scroll traces; no booking jump or pin regressions. |
| 2 — Images and delivery | Correct sizes/ratios, derivative samples and pipeline, loading policy, measured format/cache configuration | 1–2 days | Lower actual payload/decoded pixel counts at approved quality; no new image failures or cold-cache regression. |
| 3 — Whole-site pass | Oil carousel lifecycle, shared backgrounds, fonts, component boundaries, menu/modal work | 1–2 days | Representative inner routes pass visual, interaction, loading, and scrolling checks. |
| 4 — Verification and rollout | Device regression results, budgets, preview review, production comparison | 0.5–1 day | Performance and behavior gates pass; deploy through the project's normal release process. |

Stages 1 and 2 can be separate small changes so we can attribute improvements. Full scope is approximately 4.5–9 developer days, depending on visual revisions and device findings. A first useful homepage improvement should arrive before the whole-site work is complete. Keep the rendering rewrite options out of this estimate unless stages 0–2 show they are necessary.

**Measurement and acceptance plan:**

1. Reproduce on a fresh `next build` / `next start` and the matching hosted deployment. Test cold cache to identify network/decode stalls and warm cache to isolate sustained scroll rendering. Match viewport, device pixel ratio, viewport refresh rate, scroll path, and test duration. Run at least three comparable passes.
2. Test desktop Chrome and Safari, a real iPhone Safari, and a representative mid-range Android Chrome. Include a high-DPR screen and mobile portrait/landscape. CPU throttling is useful but does not reproduce a weak mobile GPU.
3. Record each scene: welcome, concept, practices, booking transition, portrait, finale. Use Chrome Performance frames/main-thread/raster tracks, paint flashing and layers where available, plus Safari Web Inspector. Examine p95 frame intervals, dropped frames, scripting/layout/paint cost, image decode, and layer area. A requestAnimationFrame counter alone does not establish compositor smoothness. [Chrome profiling reference](https://developer.chrome.com/docs/devtools/performance/reference).
4. Compare diagnostic variants individually: background filters off; header backdrop blur off; finale blur off; booking collapse removed; corrected image sizes; smaller decorative variants; then combine wins. Implement temporary switches only in local/preview profiling work and remove them from the final product flow.
5. Target consistent 60 Hz behavior on the selected 60 Hz devices: most frames within 16.7 ms, an initial project target below 5% missed frames during a controlled warm scroll, and no repeated multi-frame stalls. On 120 Hz devices also inspect the 8.3 ms cadence. These are proposed engineering gates, not current measurements; review them with the baseline and target hardware.
6. Target LCP ≤2.5 s, INP ≤200 ms, and CLS ≤0.1 at the 75th percentile, segmented by mobile/desktop when sufficient field data exists. Lighthouse loading scores and TBT are complementary; they do not verify full-page scroll smoothness or replace field INP. [Web Vitals thresholds and measurement](https://web.dev/articles/vitals).
7. Set initial transfer budgets to validate against the baseline: homepage initial images ≤250 KB on a representative mobile viewport, full-scroll image responses ≤1.5 MB on mobile and ≤3 MB on desktop. Treat these as starting budgets subject to approved image quality. Record actual decoded dimensions; aim for ordinary photos around 1–2× required display pixels and intentionally soft decoration at the smallest approved resolution. Avoid imposing a universal DPR cap on detailed logos/text artwork.
8. Verify fast/reverse scrolling, scrolling before images finish, direct deep links, anchor navigation, refresh midway through the page, back/forward restoration, orientation changes, mobile toolbar resize, font loading, and repeated route entry/exit. No hidden content, clipped artwork, stale pins, duplicate animation instances, or retained offscreen loops. Keep booking/menu/form interactions responsive while scrolling.
9. Visually compare composition, transparency edges, skin tones, crops, readable text, and desktop/mobile story timing. Reduced-motion must leave all information and controls accessible. Archive originals and retain a simple rollback path for asset and rendering changes.
10. Add CI checks for asset references/source budgets and a small production-build smoke suite for route navigation and animation cleanup. Record representative performance runs before releases; do not add brittle tests that merely mirror each tween value. Use existing analytics for field vitals if available, or scope an appropriate measurement endpoint separately.

**Next package after a production trace:** compare the existing background, header, and finale effects with isolated diagnostic variants; only then consider any rendering change that can be proven visually identical. The current package intentionally stops before those experiments: it applies the safe transform and asset work while retaining the existing blur, pinning, timing, and mobile story exactly.
